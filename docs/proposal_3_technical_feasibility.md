# 3. 기술적 실현 가능성

## (1) 오픈소스와 외부 라이브러리 활용 계획

처음부터 직접 만들기보다 이미 검증된 오픈소스를 쓰는 쪽으로 방향을 잡았다. 그리고 이건 계획서상의 이야기가 아니라, 대부분 이미 붙어서 돌아가고 있다.

분자 구조 계산은 RDKit이 맡는다. 화학정보학 쪽에서는 사실상 표준으로 쓰는 라이브러리라, 구조 정규화부터 분자 기술자 44종 계산, SMARTS 구조 패턴 82종 검출까지 전부 여기서 처리한다. 오래 검증된 도구를 쓴 덕에 계산 정확도를 우리가 따로 입증할 필요가 없다는 게 크다.

에이전트 오케스트레이션은 LangGraph로 짰다. 오케스트레이터·설계·검사·심사 노드가 하나의 그래프를 이루고, 후보 여러 개를 동시에 설계하거나 심사관을 병렬로 돌릴 때는 Send로 팬아웃한다. 검증에 걸리면 반성 단계로 되돌아가는 루프도 같은 그래프 안에 그대로 표현돼 있다. 문헌 조사에 쓰는 PubChem과 Europe PMC는 둘 다 인증 키가 필요 없어서, 어디에 배포하든 그냥 동작한다.

LLM도 한 곳에 묶이지 않게 했다. Anthropic Claude와 Groq를 같은 인터페이스 뒤에 두고 갈아 끼울 수 있게 해서, 유료 키가 없어도 Groq 무료 티어만으로 파이프라인 전체가 돈다. 처방과 판정은 전부 구조화 출력으로 받는다. 파싱이 깨지는 실패 모드 자체를 없애려고 그렇게 했고, 별도로 뭘 새로 만든 게 아니라 각 제공사가 이미 지원하는 기능을 그대로 쓴 거라 유지보수 부담도 없다.

물성 예측은 붙일 자리와 교차검증 로직까지 다 만들어 뒀고, 모델만 아직 안 붙였다. 쓰려는 건 ADMET-AI, SolTranNet, QupKake 세 가지로 모두 논문과 코드가 공개돼 있다. 앞의 둘은 PyPI로 설치되고, QupKake는 저장소를 clone해서 pip install . 한 뒤 GFN2-xTB 환경까지 따로 잡아 줘야 한다. ADMET-AI 논문 버전은 Chemprop-RDKit 기반으로 TDC의 41개 ADMET 데이터셋을 학습해 22개 TDC ADMET Benchmark Group에서 당시 최고 평균순위를 냈는데, 지금 v2는 Chemprop v2로 재학습돼서 논문 버전과 예측값이 같지 않다. SolTranNet은 SMILES 기반 Molecule Attention Transformer로 수용해도 LogS를, QupKake는 GFN2-xTB 양자화학 특징과 GNN을 엮어 site-specific micro-pKa를 예측한다.

다만 모델이 공개돼 있다는 것과, 그 예측값이 우리가 다루는 API에서 실제로 맞느냐는 전혀 다른 문제다. 그래서 이 값들은 처음부터 실험값이 아니라 "Predicted screening value"로 표시하고, 어떤 모델 버전을 썼는지, 그 분자가 모델 적용영역(applicability domain) 안에 드는지, 모델끼리 예측이 얼마나 벌어지는지를 같이 남긴다. 남은 건 ADMET-AI와 SolTranNet을 추론 파이프라인에 연결하는 것, QupKake는 xTB까지 담은 별도 이미지를 만들어 붙이는 것이다.

## (2) 제한된 자원 아래에서의 현실적 구현 방안

팀 규모와 대회 일정이라는 제약 안에서 실제로 부딪힌 문제와 그걸 어떻게 넘겼는지가 이 시스템의 실현 가능성을 가장 잘 보여준다고 본다.

Groq 무료 티어는 max_tokens까지 분당 토큰 한도에 넣어서 계산한다. 그래서 병렬 팬아웃으로 후보와 심사관을 한꺼번에 부르면 한도를 순간적으로 넘겨 호출이 거절되고, 그러면 호출부가 규칙 기반 대체값으로 내려간다. 문제는 그 대체값이 화면에서 실제 심사 결과와 구분되지 않았다는 점이다. 클라이언트가 모델별로 분당 토큰을 직접 회계하고 예산이 남은 모델에만 순번을 배정하도록 고쳤고, 대체값은 4건에서 0건으로, 실행 시간은 240초에서 123초로 줄었다. 설계상 예상치가 아니라 실제로 돌려서 잰 값이다.

비용도 무료 티어 안에서 끝나게 잡았다. 키가 아예 없어도 LLM 단계만 규칙 기반 대체로 자동 전환되고 규칙 검사·분자 계산·합의 로직은 그대로 돌아간다. 대체가 쓰인 자리에는 화면에 표시가 붙어서 실제 심사 소견과 섞이지 않는다. 덕분에 심사나 시연 도중 네트워크가 끊기거나 키가 만료돼 전체가 멈추는 상황은 구조적으로 생기지 않는다. 프런트엔드도 빌드 단계 없는 정적 대시보드라 별도 빌드 파이프라인 없이 FastAPI 서버 하나로 실시간 스트리밍까지 처리하고, 배포는 Dockerfile 하나로 로컬이든 클라우드든 똑같이 뜬다.

데이터 쪽 제약도 감추지 않고 그대로 적었다. 약학 도메인 표 42개를 받았지만 실제 판정에 쓰는 건 33개고, 나머지를 왜 뺐는지도 출처와 검증 상태가 없다는 이유를 달아 뒀다. 규칙마다 출처와 검증 상태를 표에 적고, 검증 안 된 값으로는 반려를 만들 수 없게 한 정책은 이미 한 번 스스로를 증명했다. 어린이 계면활성제 상한 규칙이 알고 보니 피부 도포용 기준이어서, 만들어 둔 데모 하나를 이 정책이 직접 걸러냈다. 자원이 부족해서 기준을 낮춘 게 아니라, 부족한 자원 안에서도 근거 없는 판정은 내리지 않겠다는 원칙을 지킨 결과다. 테스트는 pytest 54개로 구조 패턴 진리표·검사 방향·근거 정책·시나리오를 고정해 두고 실제 브라우저 동작까지 따로 확인해서, 적은 인원으로도 회귀는 잡히게 해 놨다.

남은 일도 순서를 정해 뒀다. 가장 큰 건 역시 물성 예측 모델 셋을 붙이는 작업인데, 의존성이 무거워서 배포 정책을 먼저 정하고 붙이기로 했다. 그 전까지는 "미연결"로 표시하고 실측 자료를 요청하는 지금 방식을 유지한다. 무엇이 이미 되어 있고 무엇이 남았는지, 남은 걸 언제 어떤 조건에서 붙일지까지 정해 둔 것 자체가 제한된 자원에서 실현 가능성을 담보하는 방법이라고 생각한다.
